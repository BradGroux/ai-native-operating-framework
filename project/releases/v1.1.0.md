# AI-Native Operating Framework v1.1.0

- **Status:** Prepared release candidate
- **Planned effective date:** 2026-08-22
- **Responsible steward:** Brad Groux
- **Previous release:** [v1.0.0](https://github.com/BradGroux/ai-native-operating-framework/releases/tag/v1.0.0)

## Summary

Version 1.1.0 adopts Open Framework Commons v1.1.0, resolves the two actionable
v1.0.0 audit findings, and makes release versioning forward-only. It is a
backward-compatible governance and ecosystem-context release. Framework
business meaning and requirements are unchanged.

## Open Framework Commons Adoption

AI-Native adopts the annotated Commons `v1.1.0` release:

- tag object: `79e5f06dab46f262cad1d1daf7840e683ffc3880`;
- peeled commit: `f25a2b89b4aed95984fd235e2e229efe52c125d8`;
- adopted principles: all nine;
- deferred principles: none; and
- deviations: none.

Commons v1.1.0 adds Focus Operating Framework as a fifth independent ecosystem
product and adds Commons-local repository stewardship. The shared principles
and product-independence boundaries are unchanged. AI-Native does not inherit
Commons tooling, contribution mechanics, validation, schemas, or implementation
choices.

## Issue Dispositions

- Issue 17 is accepted and corrected: the application lead-in now covers a
  business process, including both new and existing processes already listed.
- Issue 18 is accepted through ADR-011: v1.1.0 and later releases use new,
  immutable annotated tags.
- Issues 19 and 20 are valid observations of already disclosed external
  validation gaps. They do not identify false publication claims or incomplete
  framework requirements. The repository continues to prohibit claims of
  human, professional, organizational, or domain validation. A later validation
  engagement requires qualified human reviewers and separate accountable scope.

The full accountable response is recorded in the
[open-issue audit disposition](../reviews/open-issue-audit-disposition-2026-08-22.md).

## Compatibility

The release does not change:

- the charter's business meaning;
- the six concerns;
- the eight SOP content areas;
- the shared operating memory requirements;
- the six standards-maintenance activities;
- accountable human ownership;
- professional or operational boundaries;
- example status;
- licensing; or
- technology independence.

## Verification

The release candidate must pass:

- all local Markdown links and heading references;
- canonical vocabulary and framework invariants;
- all eleven examples against eight SOP content areas and six concerns;
- shared operating memory authority, provenance, handoff, privacy, retention,
  correction, recovery, and technology-independence checks;
- version, citation, workflow, YAML, and CFF validation;
- compilation and rendered-legibility checks for every Mermaid diagram;
- publication-safety and Git-history secret scans;
- separate repository-standards and release-scope reviews;
- reviewed-candidate and merged-tree identity comparison;
- passing GitHub Actions on the merged commit; and
- annotated tag and GitHub release readback.

The public GitHub release records the exact merged commit and tree after these
gates pass.

## Known Limitations

- All examples are illustrative and not domain-validated.
- The shared operating memory standard has not received human records, privacy,
  security, legal, knowledge-management, or business-continuity review.
- The framework has not been validated through live organizational use.
- Documentation and publication verification do not establish professional
  suitability, legal compliance, certification, or real-world effectiveness.
